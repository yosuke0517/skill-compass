Product story & system architecture

LLMに任せるほど、 判断力を鍛える。

Skill Compassは、AI時代のエンジニアが「知っている」だけでなく、 条件を読み、設計を選び、LLMの仕事をレビューできる専門的判断力を 隙間時間で育てる学習基盤です。

現在: 実装済みの全体像 Webも継続提供 Voice/Live中心の利用 公開可能な設計情報

The compass route

問題 LLM普及で技術キャッチアップの意欲が低下
再定義 任せるためにも、専門的な意思決定能力が必要
Skill Compass 正本データ＋実務ケース＋会話へ渡す限定能力
01

Why & pivot

このプロダクトが必要になった理由と、提供方法が変わった理由。

Webアプリから、学習の正本と会話能力へ。

出発点は、技術学習を継続するためのWebアプリでした。 ChatGPT Voice/Liveの登場で、最良の教師体験を一から作る必要はなくなりました。 そこでSkill Compassの主役を「画面」から「信頼できる学習データと、 会話へ安全に渡せる能力」に移しました。

困っていたこと

LLMが実装や調査を助けるほど、自分でCS基礎・応用・最新技術を キャッチアップする動機が弱くなっていました。

残る責任

しかし、適切な制約をLLMへ伝え、出力をレビューし、複数案から選ぶ責任は エンジニアに残ります。専門知識は不要になるのではなく、判断材料になります。

方針転換

Voice/Liveを教師のインターフェースとして活かし、Skill Compassは レビュー済み教材、個人の進捗、Podcast、X技術ニュースを保持する正本へ。 MCPでは用途ごとの限定能力だけを公開します。

現在の形

WebはToday・履歴・スキル可視化・Podcast再生の画面として残し、 日常の学習はスケジュールされた会話とVoice/Liveから始められます。

設計原則: ChatGPTがSkill Compassそのものなのではありません。Skill Compassが学習の正本を持ち、 ChatGPTにはTodayを読む、回答を同期する、Podcastを説明する、X技術ニュースを読む、 公開設計を説明する、といった目的別能力だけを渡します。
02

Learning design

定義暗記ではなく、条件に基づく実務判断を反復する。

Today's five cases train decisions.

Todayは毎日5問。短い実務シナリオとコード・SQL・API・設定・構成図を読み、 選択肢、自信度、理由を答えます。答え合わせは正誤だけで終わらず、 判断の決め手、他案の問題、実装上の注意、短い理解確認へ進みます。

Reviewed content

条件の揃った実務ケース

曖昧な前提や冗談の選択肢を避け、レビュー済みの教材だけを有効化。

Personal selection

ユーザー別の5問

弱点、復習期限、領域・ケース種別の偏り、直近履歴を考慮して選択。

Commit first

選択・自信度・理由

正解を見る前に判断を言語化。必要なら明示された条件だけをヒントにする。

Teach & retain

決め手と失敗を理解

実務への落とし込みと誤選択の結果を確認し、進捗とスコアへ反映。

現在の教材: 7領域・70問 — CS基礎、Web／バックエンド、フロントエンド、インフラ、 セキュリティ、システム／ソフトウェア設計、AI時代の開発。
03

Whole system

一つの学習コアを、Web・MCP・スケジュール・Voice/Liveから使う。

能力は分ける。学習状態は分岐させない。

表示面ごとにTodayや採点を実装せず、認証後は同じドメインサービスを呼びます。 共有するのはレビュー済み教材。分離するのは日々の割当・回答・理由・スコア・履歴です。

04

Current product

現在実装されている4つの学習・情報フロー。

Todayだけではない、日々の学習ループ。

深く考えるToday、耳で追うPodcast、変化を拾うX技術ニュース、 自分の設計を説明するArchitecture MCPを同じSkill Compassに置いています。

Practical Today

実装済み

実務ミニケースを毎日5問。Webでも、スケジュールされた会話とVoice/Liveでも、 同じレビュー済み教材と個人進捗を使います。

5 CASES → CHOICE / CONFIDENCE / REASONING → TEACH → SCORE

Podcast

実装済み

上限付きのSource snapshotから台本と音声を段階生成。 永続jobにより途中状態を残し、対話中のHTTP要求から重い処理を分離します。

COLLECT → SCRIPT → SPEECH → STORE → PLAY / ASK

X Technical News

実装済み

公開検索と、認証されたアカウントのfollowing timelineを一時的に読み、 技術関連度と反応を組み合わせて日次digestへ。投稿は事実ではなく主張として扱います。

PUBLIC + PERSONAL CONTEXT → RANK → CACHE → EXPLAIN WITH LINKS

Architecture MCP

実装済み

技術面接で構成・セキュリティ・プライバシー・トレードオフを質問可能。 回答元は人がレビューした公開manifestだけで、学習DBやファイルへ接続しません。

QUESTION → TOPIC MATCH → ALLOWLISTED FACTS → CURRENT / PLANNED
05

Security & privacy

何を共有し、誰に属し、各MCPが何をできるかを別々に制御する。

「読ませない」より先に、「能力を持たせない」。

認証だけに依存せず、コンテンツ、個人状態、ツール能力を三つの境界に分けます。 Architecture MCPには、そもそもDB・ファイル・Providerを読む機能がありません。

境界 保持するもの 制御 なぜリスクが下がるか
共有教材 レビュー済みケース、解説、出典 quality gateとseed review 回答・スコア・profileを共通コンテンツへ混ぜない。
学習状態 割当、回答、理由、score、履歴 認証済みユーザー条件をschema・repository・serviceで反復 推測したquizやanswerの識別子だけでは他ユーザーへ到達しない。
Learning MCP 要求された学習用DTO OAuth＋PKCE、bearer認証、field allowlist formやmodel入力からユーザーを選ばせず、用途外のDB列を返さない。
Architecture MCP 静的な公開manifest DB・filesystem・storage・provider能力なし prompt injectionが命令を変えても、存在しない能力は呼び出せない。
外部Provider 必要scopeのOAuth token 暗号化保存、scope制限、MCP responseから除外 password共有を避け、必要な連携単位で失効・停止できる。

将来のquery漏れ

新しいrepositoryやmigrationにも所有者条件のreviewと2ユーザーtestが必要。

manifestの人為的混入

静的でも、公開不可情報を将来追加するriskはreviewとsafety testで継続管理。

host compromise

processが利用できるsecretはhost侵害から完全には守れない。権限・更新・監視が必要。

06

Interview narrative

機能一覧ではなく、課題・判断・境界・限界の順に説明する。

面接では、作ったものより「なぜ」を話す。

Skill Compassは、プロダクト判断、学習設計、認証・認可、 非同期処理、MCPの能力設計を一つの実例として説明できます。

課題から始める

LLMで学習意欲が下がった一方、LLMを正しく使う専門判断はより重要になった。

方針転換を説明する

Webを捨てず、Voice/Liveを教師面、Skill Compassを正本と能力提供面へ再定義した。

境界で語る

共有教材と個人状態、Learning MCPとArchitecture MCP、HTTPとworkerを分離した。

限界も言う

現在はprivate local originであり、将来のquery追加やmanifest reviewには継続riskがある。

Planned

Practical diagnostic exam

約30問の実務ケースで広い領域を診断し、領域別の相対スコア （偏差値相当の指標）と技術的な得意・関心の方向を提示する構想です。

  • Todayの問題・解説UIを再利用
  • 設計判断、失敗対応、安全性を横断評価
  • 志向するcareerに合わせて提案を本人が調整
  • 診断後は日々のToday選問へ接続
Planned

Phased cloud deployment

現在のprivate local originから、契約とデータ境界を変えずに managed cloudへ段階移行する構想です。

  1. applicationとworkerの常時稼働化
  2. relational dataとgenerated assetsの移行・backup検証
  3. scheduler、observability、復旧手順のmanaged化
